# Academia Engineering Playbook

> مبني على هيكل "دليل مهندس البرمجيات" (Yehia Tech)، مطبّق تحديدًا على Academia —
> كل قسم يجاوب "شو وضعنا الفعلي هون؟" مش نظرية عامة.
> 📅 نُشئ: 6 سبتمبر 2026.

هذا الملف قسمين: **(أ)** حالة كل محور هندسي بمشروعنا فعليًا اليوم، و**(ب)** أجندة
دراسة مفتوحة (قسم 12) لقائمة المواضيع الكبيرة يلي لسا لازم قرار بشري بيها —
**مقصود إنها أسئلة مفتوحة موثّقة، مش إجابات AI افتراضية سريعة.**

---

## 1. Problem & Requirements — إحنا بنحل إيه، لمين؟

- **المشكلة:** طالب توجيهي بدون أداة عربية منظّمة تجمع المحتوى + تتبّع الأخطاء + تحضير الامتحان بمكان واحد (تفاصيل بـ`docs/product/overview.md`).
- **المستخدم:** 5 أدوار (طالب/معلم/ولي أمر/مشرف/أدمن) — كل واحد شاشاته منفصلة (`src/lib/rbac-static-data.ts`).
- **القيود الحالية:** باك اند بمرحلة مبكرة جدًا (6 controllers بس)، فريق مكوّن من 3 مطورين (فرونت + باك اند×2)، بدون فريق محتوى/تصميم مستقل.
- **معيار النجاح:** غير محدد رسميًا بعد — **قسم مفتوح، راجع الأجندة (12.5)**.

## 2. System Design — النظام يتقسم إزاي؟

```
Client → TanStack Router (SSR) → Server Functions (in-memory) → [الباك اند الحقيقي لاحقًا]
```
- **الحدود الحالية:** الفرونت بيحاكي شكل استجابة API كامل عبر `*.functions.ts`، بحيث تبديل المصدر لاحقًا = تغيير implementation داخل نفس الدالة، مش إعادة بناء الواجهة (راجع `docs/decisions/0001`).
- **Bottleneck المتوقع:** لما الباك اند الحقيقي يوصل، أكبر خطر هو schema mismatch بين شكل الـ`*-data.ts` الحالي وشكل استجابة API الحقيقي — يستحق عقد (contract) موثّق قبل الدمج، مو تخمين.

## 3. Data & Databases — البيانات تعيش فين؟

- **الحالة الحالية:** مصفوفات JS بالذاكرة (`src/lib/*-data.ts`) — تُصفَّر عند إعادة تشغيل السيرفر، ومفيهاش أي قاعدة بيانات حقيقية.
- **قرار مُتّخذ:** كل حقل بيانات جديد (زي `rating`, `studentsCount` بكتالوج الكورسات) يُضاف كـ**اختياري وفاضٍ** من الآن، حتى لما الباك اند الحقيقي يجهز يكون التعديل تعبئة بس، مو Migration.
- **مفتوح:** تصميم الـSchema الحقيقي (جداول، علاقات، مفاتيح) للباك اند نفسه — هذا شغل فريق الباك اند، موثّق كملاحظة هون بس.

## 4. Reliability — ماذا لو فشل؟

- **لا يوجد eng محدد بعد** لسيناريوهات فشل حقيقية (لأنه لا يوجد استدعاء شبكة حقيقي لخدمة خارجية بعد — كل شي in-memory).
- **مفتوح فعليًا:** لما يوصل تكامل حقيقي مع الباك اند، لازم قرار: Retry policy؟ Timeout؟ رسالة خطأ للمستخدم شكلها إيه (عندنا فعليًا `ErrorState`/`RetryButton` بـ`feedback-states.tsx` كأساس جاهز).

## 5. Security — مين مسموح له يعمل إيه؟

- **RBAC حالي:** `useAccess()` + `<Guard pageKey>` — **حجب عرض بالواجهة بس**، مش تفويض خادم حقيقي (موثّق صراحة بـ`docs/decisions/0002` و`docs/security/frontend-route-protection.md`).
- **الثغرة المعروفة والموثّقة:** أي endpoint حقيقي مستقبلي **لازم** يتحقق من الصلاحية بنفسه من الخادم، بغض النظر عن إخفاء الزر بالواجهة — هذا ليس تفصيلًا، هذا الفرق بين أمان حقيقي ووهمي.
- **Secrets:** `.env.local` (غير مرفوع)، `VITE_API_BASE_URL` هو المتغيّر الحرج الوحيد حاليًا.

## 6. Performance & Cost

- Vite + code-splitting افتراضي عبر TanStack Router (كل route ملف منفصل).
- **لم يُقَس فعليًا بعد:** Lighthouse score، Bundle size analysis، Core Web Vitals حقيقية على شبكة بطيئة. **مفتوح — راجع الأجندة (12.6)**.

## 7. Production Engineering

- Deploy عبر Vercel (`pixely-frame-magic.vercel.app`)، `npm run build` يشمل توليد `sitemap.xml`.
- **لا يوجد بعد:** Logging/Monitoring/Alerting حقيقي (لا Sentry ولا مشابه) — طبيعي بمرحلة ما قبل الإطلاق، بس لازم يكون أول شي قبل حركة مرور حقيقية.

## 8. Testing & Change

- **لا يوجد test suite حاليًا** (لا Unit ولا E2E) — فقط ESLint + TypeScript كخط دفاع أول.
- كل تعديل بهالجلسة اتحقق منه يدويًا (`patch --dry-run`, توازن أقواس, قراءة ثانية) لغياب اختبارات آلية — **هذا سد فجوة مؤقت، مو بديل عن Testing حقيقي. مفتوح — الأجندة (12.9)**.

## 9. الـ AI بيدخل فين بهالمشروع تحديدًا؟

| المنطقة | AI يسرّع | المهندس/الفريق يمتلك |
|---|---|---|
| نص/بيانات (i18n، أوصاف صفحات) | صياغة أولى بالعربي/الإنجليزي | القرار: هل النص يطابق الواقع فعليًا (قاعدة الحقيقة) |
| مراجعة كود موجود | فحص أنماط متكررة (زي `hover-lift` الخاطئ بـ40+ ملف بجلسة وحدة) | تقييم أي إصلاح فعلاً يستاهل، وترتيب الأولوية |
| كومبوننت UI جديد | كتابة أولى للـmarkup/الأنيميشن | مراجعة بصرية فعلية (AI ما بيقدر "يشوف" النتيجة بمتصفح حقيقي بهالبيئة) |
| قرار براند/UX نهائي | عرض بدائل وتحليل | القرار نفسه — دايمًا بشري |

## 10. أدرس/أبني بأي ترتيب (للفريق الجديد على المشروع)

1. Data + API fundamentals → افهم `*-data.ts` + `*.functions.ts` وليش هذا الشكل تحديدًا (قسم 3).
2. اقرأ `docs/decisions/` كامل — قرارين بس بس بيفسّروا 80% من "ليش الكود شكله هيك".
3. اقرأ `README.md` → جدول حالة الصفحات — قبل أي تعديل صفحة، اعرف حالتها.
4. System Design → `docs/architecture/frontend.md`.
5. Security boundaries → `docs/security/frontend-route-protection.md` (لتفهم شو **مش** محمي فعليًا).
6. Testing/Production → حاليًا أضعف قسمين بالمشروع، وأول شي يستاهل استثمار حقيقي.

## 11. Software Engineer Checklist (نسخة Academia)

**قبل أي Feature/صفحة جديدة:**
- [ ] شو المشكلة؟ لمين؟ (قسم 1)
- [ ] هل فيه جدول `*-data.ts` مشابه أقدر أتبع نفس نمطه بدل اختراع نمط جديد؟
- [ ] لو مافي باك اند حقيقي لهالفيتشر بعد — النص بيوصف الحاضر ولا يوهم بآلية غير موجودة؟ (قاعدة الحقيقة)
- [ ] الاسم يطابق شو المبني فعليًا، مو شو الطموح؟

**قبل أي Deploy:**
- [ ] `npm run lint` + `npm run build` نضاف.
- [ ] i18n متزامن (عربي+إنجليزي).
- [ ] أي `hover-lift`/تأثير تفاعلي مطبّق بس على عناصر قابلة فعليًا للنقر.

**بعد أي تغيير:**
- [ ] راجعت الكود قراءة ثانية (خصوصًا أي تفاعل/أنيميشن) قبل ما تعتبره خلص؟

## 12. أجندة الدراسة المفتوحة (بدون تنفيذ افتراضي — قرار بشري مطلوب لكل بند)

هاي المواضيع الكبيرة يلي محتاجة نقاش وقرار مع الفريق، **مش حل جاهز من AI بالطريق السهل**. كل بند هون سؤال موثّق، مش إجابة:

### 12.1 استراتيجية المنتج (Business Model Canvas)
- [ ] الفكرة، المشكلة، الحل — بصياغة نهائية موحّدة (فيه مسودات متفرقة بـ`docs/product/overview.md` و`market-notes.md` الأصلي، تحتاج توحيد).
- [ ] السوق المستهدف بالتفصيل (شريحة عمرية؟ جغرافيا؟ مدارس حكومية/خاصة؟).
- [ ] نموذج العمل (Business Model) — اشتراك؟ freemium؟ عمولة معلم؟ (مؤجّل بقرار سابق، بس يستاهل ورقة عمل كاملة لما يحين وقته).
- [ ] "شو بيميّزك عن غيرك؟" بصياغة نهائية مبنية على بحث تنافسي موسّع (عندنا نقطة بداية: Noon/Quizlet/Classroom/Udemy/Coursera/Abwaab/Nagwa — يحتاج تعميق).

### 12.2 Refactoring شامل من الصفر (كود + تعليقات)
- [ ] مراجعة كل تعليق بالكود: هل ضروري؟ هل واضح؟ حذف التعليقات الزائدة/البديهية، وضوح التعليقات الضرورية.
- [ ] توحيد الأنماط المتكررة بشكل مختلف بأماكن مختلفة (لو وُجدت) تحت مكوّن/دالة واحدة.
- [ ] هذا Refactoring شامل حقيقي يحتاج جلسة عمل مخصصة على مستوى الملف-الملف، مش قابل للضغط بفقرة.

### 12.3 تحليل شامل لنظام التصميم (Design System Audit)
- [ ] **الخط:** قرار نهائي (Cairo+Reem Kufi الحاليين، ولا استبدال بهوية مخصصة بالكامل؟).
- [ ] **الشعار (Logo):** غير موجود تصميم رسمي مستقل حاليًا — بند مفتوح بالكامل.
- [ ] **الألوان:** قرار براند نهائي (مؤجَّل عمدًا لآخر المشروع، بس البنية الحالية tokenized فيخلي القرار رخيص التنفيذ لاحقًا).
- [ ] **المحتوى:** مراجعة نبرة الصوت (Tone of voice) موحّدة عبر كل الصفحات.
- [ ] **الصفحات:** أي صفحة إضافية مطلوبة غير الموجودة؟ (راجع 12.11 لصفحة Onboarding تحديدًا).
- [ ] **التأثيرات/الأنيميشن:** تدقيق شامل (بدأناه جزئيًا — hover states، illustrations) بس يحتاج جولة تصميم مخصصة، مو تصحيحات متفرقة.
- [ ] **الصور والأيقونات:** مصدر نهائي للصور (تصوير حقيقي؟ AI مولّدة بـPrompt موحّد؟ — طلب سابق لسا معلّق لحد ما تُحسم قرارات المحتوى/الألوان أولاً).

### 12.4 SEO
- [ ] تدقيق meta tags/structured data الحالية فعليًا (موجودة بنية أساسية بـ`src/lib/seo.ts`، بس ما اتفحصت بعمق بعد لجودة المحتوى نفسه لمحركات البحث).
- [ ] استراتيجية كلمات مفتاحية عربية فعلية.

### 12.5 الخصوصية والصلاحيات والفروق الفردية
- [ ] سياسة خصوصية مفصّلة تتجاوز صفحة `/privacy` العامة (خصوصًا بيانات القاصرين — طلاب توجيهي أغلبهم قاصرين).
- [ ] فروق الوصول الحقيقية بين الأدوار (Access الحالي واجهة بس — قسم 5) لحد ما يوصل تفويض خادم حقيقي.
- [ ] إمكانية الوصول (Accessibility/a11y) لذوي الإعاقة — **لم يُفحص فعليًا بأدوات حقيقية** (screen reader, keyboard-only navigation, أدوات زي axe/Lighthouse a11y) — بند مفتوح كامل، يستاهل جلسة تدقيق مخصصة.

### 12.6 UI/UX من الصفر (بخطة محكمة، مش بدون خطة زي الحالي)
- [ ] مراجعة شاملة بنظريات UX معروفة (Nielsen's heuristics، Fitts's Law، Hick's Law...) على كل شاشة، مو تصحيحات نقطية.
- [ ] Design tokens/spacing/typography scale — تدقيق شامل موحّد (فحصنا أجزاء بس هالجلسة).

### 12.7 Clean Code
- [ ] معايير موحّدة موثّقة (تسمية، حجم دالة أقصى، تكرار مسموح به) — موجود جزء بـ`docs/standards/code-style.md`، يحتاج توسيع.

### 12.8 مبادئ التسويق
- [ ] استراتيجية محتوى/نشر (المدونة موجودة، بس بلا خطة نشر منتظمة موثّقة).
- [ ] قنوات اكتساب مستخدمين — غير محدد بعد.

### 12.9 QA / Testing
- [ ] لا يوجد test suite حاليًا (قسم 8) — قرار: أولوية Unit tests ولا E2E أولًا؟ أي أداة (Vitest؟ Playwright؟).

### 12.10 فيتشرز مميزة إضافية
- [ ] بنك الأخطاء + المراجعة اليومية (الميزة التنافسية الأساسية المستهدفة) — **لسا مو مبني فعليًا** (قسم 12 بـREADME)، أولوية بناء حقيقية تحتاج جدولة مع فريق الباك اند.
- [ ] أي فيتشرز تانية مميزة — مفتوح للنقاش.

### 12.11 Onboarding
- [ ] **لا توجد صفحة/تجربة Onboarding حاليًا.** أول مرة يسجّل فيها مستخدم جديد (أي دور)، بيوصل مباشرة للوحة التحكم الفاضية بدون أي توجيه. هذا فراغ حقيقي يستاهل تصميم مخصص (تختلف احتياجاته حسب الدور — طالب يحتاج "أضف أول مادة"، معلم يحتاج "أضف أول كورس"، ولي أمر يحتاج "اربط أول ابن").

### 12.12 شغلات تانية ما اتذكرت
- [ ] هذا القسم مقصود يبقى مفتوح — أي فكرة جديدة تنضاف هون بدل ما تضيع بمحادثة.

---

**تذكير أخير (نفس مبدأ الأجندة فوق):** أي بند بالقسم 12 لو طُلب من AI تنفيذه مباشرة بدون نقاش، ارجع لهالملاحظة — القرار الافتراضي للـAI مو بالضرورة القرار الصح لمشروعكم.
